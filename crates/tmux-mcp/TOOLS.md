## Reading retained pane output

Reading old output does not require copy mode. `capture_pane` reads the visible
screen by default; set `history: true` to include retained scrollback. Use its
`start` and `end` bounds when only a known range is relevant.

`snapshot_pane` returns terminal content with cursor, geometry, and mode metadata
in one MCP call. The state query and capture are separate tmux operations, so the
result is not an atomic view of a pane that changes during the call.

`search_panes` searches visible screens by default and retained scrollback with
`history: true`. It is the bounded way to find which pane contains known text
without capturing every pane into the client's context.

Use `capture_since` for later output. Keep its opaque cursor and check `missed`;
a gap can mean the pane outran the buffer, its live tail was evicted, or the
server restarted. The current text is then not complete history. Cursors observe
output without changing pane state.

## Respecting human-owned pane modes

`snapshot_pane` reports `in_mode`, `mode`, and `scroll_position` when tmux owns
the pane's input. These fields are observations, not permission to change the
attached person's view, selection, key table, or clipboard state.

The MCP does not enter or cancel pane modes. Enter/exit pairs have unclear
ownership when a client disconnects, and cancelling can discard a person's
selection or close a different mode than the caller assumed.

Keep observing with capture, snapshot, search, `capture_since`, or
`wait_for_text`. Pane-input tools refuse dead or mode-owned configured
recipients. `send_keys_batch` repeats that check for each executed row, while
`paste_text` targets only the named pane and checks before buffer creation.

`run_shell_command` requires one configured recipient and checks its cohort,
mode, liveness, and foreground command before watcher setup and before
dispatch. These are observations, not locks: state can still change before
tmux processes input, and returned pane IDs do not confirm delivery.

The `libtmux` crate retains `Pane::copy_mode` and `Pane::exit_mode` for
applications that own the complete interaction. Library parity does not require
the detached MCP surface to expose modal human-client operations.

## `run_shell_command`

Run a shell command in a pane with your user's permissions. Run a shell command in a pane, wait for it to finish, and report its exit status with everything it wrote. This is the tool for "run this and tell me if it worked". Output is read from the pane's live stream, so nothing is missed and the shell prompt is not included. The command runs in a subshell, so cd and export do not persist and invalid syntax completes with a nonzero status. It requires one configured input recipient and observes its mode, liveness, cohort, and foreground command before watcher setup and again before dispatch. These checks do not lock the pane and can race with tmux processing the input. The pane must run a trusted POSIX-compatible shell whose reserved words and special builtins retain their meanings, against a trusted tmux server and configuration. Reaching the deadline or cancelling this request stops the waiting, not the command; inspect the pane before sending more input.
